# LLM 与规则引擎的分工

> 核心问题：NPC 哪些行为用 LLM，哪些用规则引擎？（对应 TinyMB 开放问题 O2）

---

## 一、Claude Code 的混合架构参考

Claude Code 本身就是一个 LLM + 规则引擎的混合系统：

| 功能 | 由谁负责 | 为什么 |
|---|---|---|
| 决定调用哪个工具、传什么参数 | LLM | 需要理解用户意图和上下文 |
| 校验参数是否合法（schema） | 规则引擎（Zod） | 确定性，不能有随机性 |
| 判断操作是否安全（权限） | ML 分类器 + 规则 | 混合：ML 做初筛，规则做兜底 |
| 文件读写、命令执行 | 确定性工具代码 | 系统操作必须精确 |
| 生成回复文本 | LLM | 自然语言生成是 LLM 核心能力 |
| 上下文压缩/摘要 | LLM | 需要理解语义 |
| Token 计数、成本计算 | 规则引擎 | 数学计算必须精确 |

## 二、TinyMB 的推荐分工方案

### 2.1 总体原则

```
LLM 做决策和生成 —— "选什么" + "怎么说"
规则引擎做校验和结算 —— "能不能" + "结果是什么"
```

### 2.2 按行为类型的详细分工

| 行为类型 | 引擎 | 理由 | 成本等级 |
|---|---|---|---|
| **日常行为选择**（去哪、做什么） | LLM | 需要综合性格、记忆、关系做开放式判断 | 中 |
| **社交对话内容** | LLM | 自然语言生成是核心能力 | 中 |
| **长期目标调整** | LLM | 需要根据局势变化做开放式推理 | 高 |
| **派系投票/站队决策** | LLM（决策）→ 规则（执行） | 性格驱动但结果确定 | 高 |
| **战斗结算** | 规则引擎 | 确定性 + 公平性 | 零 LLM |
| **经济交易** | 规则引擎 | 数值精确性 | 零 LLM |
| **移动/位置更新** | 规则引擎 | 确定性空间逻辑 | 零 LLM |
| **事件触发判断** | 规则引擎（概率表） | 概率确定性 | 零 LLM |
| **事件叙事包装** | LLM | 内容多样性和角色化 | 低 |
| **日记生成** | LLM | 叙事质量 | 中（但频率低） |
| **NPC 情绪/评价更新** | 规则引擎为主 + LLM 辅助 | 基础变化用公式，特殊情况用 LLM | 低 |

### 2.3 混合流程示例

以"NPC 决定是否参加护卫任务"为例：

```
┌──────────────────────────────────────────────────┐
│ Step 1 [规则引擎]：生成可用行动清单                 │
│   - 当前位置：酒馆区                               │
│   - 可用行动：喝酒、对话、接受任务、离开...          │
│   - 过滤掉不满足前置条件的行动                       │
├──────────────────────────────────────────────────┤
│ Step 2 [LLM]：Agent 决策                           │
│   输入：角色状态 + 可用行动 + 近期记忆 + 目标        │
│   输出：结构化行动意图                               │
│   {                                                  │
│     "action": "accept_quest",                        │
│     "target": "escort_caravan",                      │
│     "reasoning": "报酬不错，而且能加深和商盟的关系"   │
│   }                                                  │
├──────────────────────────────────────────────────┤
│ Step 3 [规则引擎]：校验与结算                        │
│   - 检查：NPC 是否有空余时间步？资源够吗？           │
│   - 扣除资源                                         │
│   - 设置任务状态                                     │
│   - 计算结果概率                                     │
├──────────────────────────────────────────────────┤
│ Step 4 [规则引擎]：事件触发                          │
│   - 商盟关系 +5                                      │
│   - 触发"护卫路上的随机遭遇"                         │
├──────────────────────────────────────────────────┤
│ Step 5 [LLM，可选]：叙事包装                         │
│   - 生成事件的文字描述，供日记和玩家观察使用          │
└──────────────────────────────────────────────────┘
```

## 三、降成本策略：哪些 LLM 调用可以跳过

[TinyMB 对接] 风险 R7（LLM 调用成本超预算）。

### 3.1 低优先级 NPC 用规则引擎替代

不是所有 NPC 每个 tick 都需要 LLM 决策：

- **远离玩家的 NPC**：用规则引擎驱动（基于性格的行为概率表）
- **处于稳定状态的 NPC**：如果连续 3 步没有显著事件，降级为规则引擎
- **日常行为**：大部分日常行为可以用预设的行为模板 + 随机选择

### 3.2 何时必须用 LLM

- NPC 与玩家直接对话时
- NPC 面临重大决策时（站队、战斗、交易超过阈值）
- NPC 遭遇意外事件时（被攻击、发现秘密、收到请求）
- 生成日记/摘要时
- 玩家主动查看 NPC 的"想法"时

### 3.3 预生成 vs 实时生成

Claude Code 的 prefetch 机制（`prefetch.ts`）在空闲时预加载可能需要的数据。

**TinyMB 可以预生成**：
- 通用的日常对话模板（"天气不错啊"、"生意怎么样"级别的闲聊）
- 常见事件的叙事描述变体
- NPC 的通用内心独白模板

**必须实时生成**：
- 和玩家的对话回复
- 关键决策的 reasoning
- 日记中关于特定事件的个人化反思

## 四、LLM 调用失败时的规则引擎兜底

参考 Claude Code 的错误恢复策略：

| 故障类型 | 兜底方案 |
|---|---|
| LLM 超时 | 使用角色的默认行为模板 |
| LLM 返回不合法的行动 | 规则引擎从可用行动中随机选择一个低风险行动 |
| LLM 返回空内容 | 当作"等待/观望" |
| API 配额耗尽 | 所有 NPC 切换到纯规则引擎模式直到配额恢复 |

这保证了即使 LLM 服务中断，世界也能继续运转——只是 NPC 的行为会变得更"模式化"和"可预测"，但不会崩溃。

## 五、对开放问题 O2 的总结回答

> NPC 哪些行为用 LLM，哪些用规则引擎？

**回答**：不是非此即彼，而是**混合管线**——LLM 做需要理解/生成的部分（决策、对话、日记），规则引擎做需要确定性的部分（校验、结算、事件触发）。大多数行为是两者协作完成的。

降本的关键不是"少用 LLM"，而是**分级调用**：
- 远离玩家关注的 NPC → 规则引擎为主
- 接近玩家关注的 NPC → LLM 为主
- 日常行为 → 可以用规则引擎
- 关键事件 → 必须用 LLM
