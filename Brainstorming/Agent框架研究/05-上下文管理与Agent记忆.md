# 上下文管理与 Agent 记忆

> 核心问题：如何在有限 token 预算内管理 Agent 的长期/短期记忆？日记怎么生成？记忆怎么检索？

---

## 一、Claude Code 的三层压缩策略

[源码锚点] `autoCompact()` 在 `query.ts` 主循环中。压缩相关模块分布在 `compact/` 目录下（`reactiveCompact.js`、`snipCompact.js`、`cachedMCConfig.js` 等，多数被 feature gate 移除但有接口签名）。

### 1.1 Microcompact（微压缩）

- 将**过时的工具输出**替换为占位符
- 保留叙事脉络，丢弃具体数据
- 触发条件：工具结果已被后续步骤覆盖

### 1.2 Auto-compact（自动压缩）

- 在 token 使用达到 **~87%** 上下文容量时自动触发
- 对整个对话历史做摘要
- 有**熔断器**：连续失败 3 次后停止（`MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`）
- 摘要指令要求"只输出文本，不使用工具"——防止摘要过程中触发新的工具调用

### 1.3 Full Summarization（全量压缩）

- 用户主动触发（`/compact`）或系统强制触发
- 对完整对话做全面摘要
- 摘要结果替换原始对话历史

### 1.4 Memory Retrieval（记忆检索）

- 使用**辅助模型**（如 Sonnet）对 memory 文件按标题/描述打分
- **Precision over recall**：宁可少选，不可错选
- **Cap ~5 items**：每次检索最多返回约 5 条记忆

## 二、TinyMB Agent 记忆的三层映射

| 层级 | Claude Code 对应 | TinyMB 实现 | 触发时机 |
|---|---|---|---|
| 工作记忆 | Microcompact | 每步行动后，用关键变化替换完整历史细节 | 每个行动步之后 |
| 短期记忆 | Auto-compact | 对近期 N 步事件做结构化摘要 | 每 3~5 步，或 token 接近上限时 |
| 长期记忆 | Full summarization + Memory files | 角色日记/历史档案，持久存储 | 每个结算周期（每 3 天） |

### 2.1 工作记忆

每个时间步，Agent 收到的观察包只包含：

- 当前步直接可见的信息
- 上一步的行动结果
- 最近 2-3 个事件的简短描述

不包含：

- 更早之前的完整对话历史
- 其他区域发生的所有事件
- 已过时的状态数据

### 2.2 短期记忆

每隔若干步（或在上下文快满时），由 Runtime 对 Agent 的近期经历做摘要：

```
短期记忆摘要示例：
- 你在过去两天中：
  - 从外城农庄移动到市集区
  - 花费 50 金币购买了粮食
  - 与商人 Vorn 交谈，他提到商盟正在招募护卫
  - 在酒馆听到守备军团最近在加强巡逻
- 你的声望从 12 涨到 15
- 你与商盟的关系从"中立"变为"友好"
```

### 2.3 长期记忆（日记系统）

[TinyMB 对接] 开放问题 O3：日记生成的 prompt 设计。

参考 Claude Code 的 transcript 机制，日记不是让 NPC LLM 每步都写，而是：

1. **积累事件缓冲区**：Runtime 在每步记录关键事件（结构化数据）
2. **周期性生成**：在结算点（每 3 天）调用 LLM，以角色视角对这些事件写一篇日记
3. **日记 prompt 模板**：

```
你是 [角色名]，性格是 [性格描述]。
过去三天发生了以下事件：
[事件列表，按时间排序]

请以第一人称写一篇简短的日记（3-5 段），反映你对这些事件的感受、思考和打算。
注意：
- 符合你的性格
- 包含对其他角色的评价变化
- 如果有重要决策，解释你的理由
- 可以包含对未来的计划或担忧
```

4. **日记持久存储**：写入角色的长期记忆文件
5. **日记可见性**：玩家可以阅读自己 Agent 的日记；NPC 日记根据亲密度分级可见

## 三、记忆检索策略

当 Agent 需要回忆过去的信息时（比如"上次我和 Vorn 说了什么？"），不要把所有历史记忆塞进 context，而是用 Claude Code 的方式做精准检索：

### 3.1 索引层

为每条长期记忆建立索引：

```json
{
  "memory_id": "day_6_diary",
  "title": "第 6 天日记 - 加入商盟护卫队",
  "tags": ["商盟", "Vorn", "护卫", "战斗"],
  "timestamp": "day_6",
  "summary": "接受了 Vorn 的护卫任务，在外城遭遇了匪徒，成功击退但损失了 2 名随从"
}
```

### 3.2 检索流程

```
当前情境（Agent 正在和 Vorn 对话）
  → 提取关键词 ["Vorn", "商盟", "对话"]
  → 在索引层搜索匹配的记忆（按相关性排序）
  → 取 Top 3~5 条记忆的完整内容
  → 注入到 Agent 的动态 prompt 层
```

### 3.3 简化实现

如果不想引入单独的检索模型，可以用更简单的方式：

- **基于标签匹配**：当前情境中出现的 NPC 名字 / 地点 / 事件类型，匹配记忆的 tags
- **时间衰减**：最近的记忆权重更高
- **重要性标记**：关键事件（战斗、站队、背叛）的记忆永远有较高的召回权重

## 四、Auto-compact 熔断的游戏版

Claude Code 的 auto-compact 有每天约 250k 浪费 API 调用的教训。TinyMB 也需要类似的保护：

- 如果 Agent 连续 3 次生成不合法的行动意图 → 熔断，执行默认安全行为
- 如果记忆摘要连续 2 次质量过差（如丢失关键信息）→ 切换到更简单的摘要策略
- 设定每个 Agent 每结算周期的 **LLM 调用预算上限**

## 五、"Dream Task" 的启发

[源码锚点] Claude Code 有一个 feature-gated 的 "DreamTask"（`tengu_onyx_plover`）——后台记忆整合。

**TinyMB 可以借鉴的"梦境"机制**：

在每个结算周期的"夜间"阶段，对 NPC 的记忆做一次整合：

- 合并重复的记忆片段
- 标注过时的信息（"Vorn 曾经是盟友，但现在关系破裂了"）
- 提取模式（"守备军团最近一直在扩张"）
- 生成"预感"或"直觉"，可以影响下一天的行为倾向

这在叙事上还能表现为"NPC 做了一个梦"或"NPC 在夜里辗转反侧想明白了一些事"。
