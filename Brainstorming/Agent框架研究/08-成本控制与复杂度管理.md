# 成本控制与复杂度管理

> 核心问题：如何控制 LLM 调用成本、防止系统复杂度失控、设定有效的熔断机制？

---

## 一、Claude Code 的成本与复杂度控制手段

### 1.1 Prompt Cache 经济学

[源码锚点] `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`、`promptCacheBreakDetection`（14 个 cache-break 向量）。

- 静态 prompt 前缀缓存后，后续请求只按**缓存读取**计费（通常是全价的 1/10）
- 频繁切换模式（plan → agent → debug）会破坏缓存，增加成本
- "Sticky latches" 防止不必要的模式翻转

### 1.2 熔断机制

- `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`：auto-compact 连续失败 3 次后停止
- 遥测数据显示每天约 250k 浪费的 API 调用来自失控的 auto-compact 循环

### 1.3 成本追踪

[源码锚点] `cost-tracker.ts`——实时累积 API 调用成本。

### 1.4 分级调用策略

- 不同任务用不同质量的模型（如 Sonnet 做记忆检索，Opus 做核心推理）
- 工具描述按需注入（lazy loading），减少每次请求的 token 数

## 二、TinyMB 的成本控制方案

### 2.1 每 Tick 成本模型

以 6 NPC + 1 玩家、每天 2 tick 为例：

```
每 tick 最大 LLM 调用次数：
  - 7 个 Agent 各调用 1 次决策 = 7 次
  - 可能的对话生成 = 0~3 次
  - 事件叙事包装 = 0~2 次
  最大 ≈ 12 次/tick

每天（2 tick）：最大 ≈ 24 次
每结算周期（3 天）：最大 ≈ 72 次 + 日记生成 7 次 = 79 次
```

### 2.2 降本手段

| 手段 | 预期节省 | 实现复杂度 |
|---|---|---|
| **共享 prompt cache**（所有 NPC 共用静态前缀） | ~60-80% prompt token 费 | 低 |
| **远离玩家的 NPC 降级为规则引擎** | ~30-50% 调用次数 | 中 |
| **日常行为跳过 LLM** | ~20-30% 调用次数 | 低 |
| **使用较便宜的模型做日常决策** | ~50-70% 单次费用 | 低 |
| **预生成通用对话/描述模板** | ~10-20% 调用次数 | 中 |
| **合并多个 NPC 的简单行为到一次 batch 调用** | ~20% 调用次数 | 高 |

### 2.3 分层模型策略

参考 Claude Code 用不同模型做不同任务：

| 任务类型 | 推荐模型等级 | 理由 |
|---|---|---|
| 核心决策（站队、战斗、外交） | 高质量模型 | 需要深度推理 |
| 日常行为选择 | 中等模型 | 够用即可 |
| 对话生成（与玩家） | 高质量模型 | 直接影响体验 |
| 对话生成（NPC 之间） | 中等模型 | 除非玩家在场 |
| 日记生成 | 中等模型 | 频率低，可以接受稍低质量 |
| 记忆检索/打分 | 低成本模型 | 只需要评分，不需要生成 |
| 事件叙事包装 | 低成本模型 | 短文本，模板化程度高 |

## 三、复杂度管理

### 3.1 FateClaw MVP v1 的教训

FateClaw 因复杂度过高被封存。核心教训：

- 7 个 Master + 7 个 Servant + 圣杯战争规则 = 复杂度爆炸
- "先回答'最小系统是什么'，再决定保留哪些细节"

### 3.2 Claude Code 的复杂度管理模式

- **Feature gate 矩阵**：每个新能力都绑定一个开关，可以独立开/关
- **分阶段交付**：不同 feature 在不同阶段上线（如 KAIROS、Voice、Coordinator 各自有自己的 gate）
- **Dead-code elimination**：编译时移除未启用的功能模块

### 3.3 TinyMB 的复杂度红线

[TinyMB 对接] 极简骑砍规则集自审检查清单。

| 维度 | 红线 | 超出红线的应对 |
|---|---|---|
| NPC 数量 | 首轮 6 名 | 用规则引擎驱动额外的"群众"NPC |
| 区域数量 | 首轮 4 个 | 新增区域放 Later |
| 行动类型 | 首轮 ~15 种 | 新增行动类型需要经过"是否影响核心循环"评审 |
| 数值维度 | 11 种角色 + 6 种世界变量 | 新增变量必须证明"不加就无法支撑核心体验" |
| 每 tick LLM 调用 | ≤12 次 | 超出时降级远离玩家的 NPC |
| 单次 prompt token | ≤4000 tokens | 超出时触发压缩/裁剪 |

### 3.4 Feature Gate 在游戏中的应用

参考 Claude Code 的 feature gate 模式，TinyMB 可以为可选机制设置开关：

```
feature_flags:
  RANDOM_ENCOUNTERS: true        # 移动随机事件
  EXTERNAL_PRESSURE: false       # 外部压力系统（Later）
  FACTION_VOTING: false          # 派系议事投票（Later）
  FOUR_LEVEL_AUTONOMY: false     # 四级自主等级（首轮只用 L2）
  NPC_DIARY_VISIBLE: true        # NPC 日记可见性
  ECONOMIC_FLUCTUATION: false    # 物价波动（Later）
```

开发时可以逐一开启测试，而不是一次性把所有功能都加进去。

## 四、熔断与降级策略

### 4.1 LLM 层面

| 触发条件 | 熔断行为 |
|---|---|
| Agent 连续 3 次输出不合法行动 | 切换到规则引擎模式 |
| 单 tick LLM 调用超过 15 次 | 剩余 NPC 本 tick 用规则引擎 |
| 单日总调用超过预算 80% | 所有非玩家直接交互的 NPC 降级 |
| API 返回 429（速率限制） | 全体降级到规则引擎，指数退避重试 |
| API 返回 5xx 错误 | 暂停世界推进，通知玩家 |

### 4.2 世界状态层面

| 触发条件 | 熔断行为 |
|---|---|
| 经济数值偏离合理范围 >50% | 触发"自然灾害/市场调控"事件修正 |
| 同一 NPC 连续 5 步做相同行为 | 标记为"行为异常"，人工审查 |
| 世界状态一致性检查失败 | 暂停结算，回滚到上一个一致状态 |
| 玩家报告"这不合理" | 记录反馈，纳入下次规则调整 |

## 五、可审计性是信任的基础

Claude Code 有完整的 transcript 和 telemetry。TinyMB 也应该建立审计体系：

### 5.1 审计日志内容

每个行动记录：
- 谁（Agent ID）
- 什么时候（tick 编号）
- 做了什么（行动类型 + 参数）
- 为什么（LLM 的 reasoning，如果是 LLM 决策）
- 结果是什么（成功/失败 + 状态变化）
- 花了多少（LLM 调用 token 数和成本）

### 5.2 审计的价值

- **调试**：NPC 做了不合理的事 → 查审计日志看 reasoning
- **成本分析**：哪个 NPC/哪类行为消耗最多 LLM token
- **平衡调优**：经济/关系数值的变化趋势
- **玩家体验**：玩家可以翻看"Agent 为什么做了这个决定"

[Trumen 对接] worldboxBot 的 `AuditRecord` 契约和 `audit.jsonl` 已经在走这条路。TinyMB 可以直接复用或参考其设计。
