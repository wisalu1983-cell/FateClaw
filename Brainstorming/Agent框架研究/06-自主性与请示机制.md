# 自主性与请示机制

> 核心问题：从 Claude Code 的权限系统到 TinyMB 的四级自主等级，如何平衡 Agent 自主性和玩家控制感？

---

## 一、Claude Code 的权限系统

[源码锚点] `permissions.ts`，以及 `bypassPermissionsKillswitch.ts`、`autoModeState.ts` 等。

### 1.1 三种权限模式

| 模式 | 行为 | 适用场景 |
|---|---|---|
| `default` | 每次高风险操作询问用户 | 普通使用 |
| `bypass` | 自动允许所有操作 | 信任场景 / YOLO 模式 |
| `strict` | 自动拒绝所有未明确允许的操作 | 高安全场景 |

### 1.2 工具级粒度控制

- 每个工具独立配置权限策略
- 持久化存储权限规则
- 基于 ML 的分类器自动推断操作安全性

### 1.3 "接受或退出" 模型

远程安全配置变更时：拒绝 = 程序退出。这是一种"框架层强制约束"而非"prompt 层建议"。

## 二、TinyMB 四级自主等级的对照设计

[TinyMB 对接] 极简骑砍规则集 §2.1 和 05-玩家引导与请示节奏.md。

### 2.1 四级自主等级

| 等级 | 名称 | Claude Code 对应 | 行为 |
|---|---|---|---|
| L1 | 完全托管 | `bypass` 模式 | Agent 自主执行所有行动，只在日记中记录，不中断玩家 |
| L2 | 重要请示 | `default` 模式 | 日常自主，高风险行动暂停请示玩家 |
| L3 | 频繁请示 | `default` + 更多工具需要权限 | 大部分非日常行动都请示，只有基本日常行为自主 |
| L4 | 完全控制 | `strict` 模式 | 每个行动都需要玩家确认 |

### 2.2 首轮 MVP 推荐策略

极简骑砍规则集定义的首轮方案：**"默认自主 + 重要请示 + 安全回退"**，对应 L2 等级。

具体规则：

```
请示触发条件（L2 等级）：
- 花费超过身家 30% 的行动 → 请示
- 战斗行为 → 请示
- 派系站队表态 → 请示
- 接受/拒绝重要任务 → 请示
- 主动攻击任何角色 → 请示
- 放弃当前目标 → 请示

自主执行：
- 区域间移动
- 小额交易
- 日常对话
- 信息收集
- 休息/吃饭
```

## 三、请示机制的实现细节

### 3.1 请示不是阻塞世界

Claude Code 的权限询问会暂停当前工具执行。但游戏中不能因为等待玩家确认就让整个世界停下来。

**推荐设计**：

- 玩家 Agent 的行动被暂停，等待确认
- 世界其他部分继续运行（NPC 继续行动）
- 如果玩家超时未回复：
  - 低风险行动 → 自动执行（按 Agent 建议）
  - 高风险行动 → 安全回退（Agent 选择等待/观望）

### 3.2 请示的信息呈现

参考 Claude Code 在请求权限时的信息展示（工具名称 + 参数 + 风险描述），请示界面应包含：

```
┌─────────────────────────────────────────┐
│ 🔔 你的 Agent 请求确认                    │
│                                           │
│ 行动：接受 Vorn 的护卫任务                 │
│                                           │
│ Agent 的想法：                             │
│ "这个任务报酬不错（80 金币），而且能提升    │
│  和商盟的关系。但路途有风险，我们可能遇到   │
│  匪徒。"                                  │
│                                           │
│ 预计代价：需要出城 1 天，消耗 10 粮食       │
│ 预计风险：可能遭遇战斗                      │
│ 预计收益：+80 金币，+5 商盟关系             │
│                                           │
│ [✅ 同意] [❌ 拒绝] [📝 修改指令]          │
└─────────────────────────────────────────┘
```

### 3.3 积压合并

如果玩家离线期间积累了多个请示：

- 合并同类请示（"你的 Agent 在过去 2 天中有 3 次想购买粮食"）
- 按时间倒序展示，优先显示最新/最重要的
- 过期的请示自动按安全回退处理

## 四、从 KAIROS 模式学到的自主性梯度

[源码锚点] KAIROS 根据用户是否在终端前动态调整自主程度：离焦点越远，自主性越高。

**TinyMB 的动态自主性**：

| 玩家状态 | Agent 行为 |
|---|---|
| 在线且活跃 | 按当前自主等级运行，请示立即推送 |
| 在线但闲置（5 分钟无操作） | 自主等级自动提升一档 |
| 离线 | 自动进入 L1（完全托管），所有请示积压 |
| 回到在线 | 恢复原自主等级，展示积压的请示和日记摘要 |

### KAIROS 的 Tick 心跳对照

KAIROS 有 `<tick>` 定时自检"还有什么要做的"。TinyMB 的半天制就是一种 tick：

- 每半天一次 tick → Agent 做一次 Observe→Think→Decide→Act
- 在 NPC 无特殊事件时，可以跳过某些 tick 的 LLM 调用（用规则引擎处理默认行为）
- 在重大事件发生时，可以插入额外 tick（如被攻击时立即触发反应）

## 五、权限规则不要硬编码在 Prompt 中

Claude Code 把权限规则放在 `permissions.ts` 中，和 prompt 分离。TinyMB 也应该如此：

**反模式**：在 NPC 的 system prompt 里写"当花费超过 30% 身家时你必须询问玩家"

**推荐做法**：
- 权限规则存在 Runtime 的配置中
- Agent 只知道"提交行动意图"
- Runtime 根据配置决定是否需要请示
- Agent 收到的反馈是"此行动需要玩家确认，请等待"

这样做的好处：
- 权限规则可以在不修改 prompt 的情况下调整
- Agent 无法"学会"绕过权限检查
- 权限逻辑的行为是确定性的，不受 LLM 随机性影响

[TinyMB 对接] 极简骑砍规则集 §2.1.1："多层约束——官方系统 prompt 锁定行为框架 → Server/Runtime 校验行动合法性 → Server/Runtime 结算产生权威结果"。权限规则属于 Runtime 校验层。
