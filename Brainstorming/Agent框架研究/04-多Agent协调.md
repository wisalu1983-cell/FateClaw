# 多 Agent 协调

> 核心问题：6 个 NPC + 1 个玩家 Agent 在同一世界中如何高效协调，避免冲突、降低成本？

---

## 一、Claude Code 的 Coordinator 模式

[源码锚点] `coordinatorMode.ts` — 用 system prompt 指令定义管理者行为，而非复杂编程逻辑。

### 核心设计原则

1. **并行阶段和串行阶段明确分开**——搜索/信息收集可并行，状态修改必须串行
2. **子代理不能再生成子代理**——防止嵌套失控
3. **共享 prompt 前缀**优化 cache hit rate
4. **父代理必须给子代理具体路径/行号**——不允许"你去看一下"式的模糊委托

### 角色分离

Claude Code 定义了不同角色的 Agent：

- **Explore / Plan agents**：只读权限，Bash 限制为安全命令（`ls`、`git status`）
- **Implementation agents**：完整工具权限
- **Verification agent**：对抗性姿态，"试图打破它"，必须运行 build/tests/lint

## 二、TinyMB 多 Agent 协调方案

### 2.1 两阶段处理模型

每个时间步（半天制），7 个 Agent 的处理分为两个阶段：

```
┌────────────────────────────────────────────────┐
│ 阶段 1：并行感知/决策                            │
│                                                  │
│  ┌──────┐  ┌──────┐  ┌──────┐  ... ┌──────┐   │
│  │NPC-1 │  │NPC-2 │  │NPC-3 │      │Player│   │
│  │感知   │  │感知   │  │感知   │      │感知   │   │
│  │决策   │  │决策   │  │决策   │      │决策   │   │
│  │意图   │  │意图   │  │意图   │      │意图   │   │
│  └──┬───┘  └──┬───┘  └──┬───┘      └──┬───┘   │
│     │         │         │              │        │
│     ▼         ▼         ▼              ▼        │
│  ┌──────────────────────────────────────────┐   │
│  │        行动意图队列（有序）                │   │
│  └──────────────────────────────────────────┘   │
├────────────────────────────────────────────────┤
│ 阶段 2：串行校验/结算                            │
│                                                  │
│  按优先级逐个处理行动意图：                       │
│  1. 校验合法性（前置条件在当前世界状态下是否满足） │
│  2. 检测冲突（两个 NPC 想占同一资源）             │
│  3. 执行结算（按优先级决定谁成功）                │
│  4. 更新世界状态                                  │
│  5. 记录审计日志                                  │
└────────────────────────────────────────────────┘
```

### 2.2 并行感知的好处

- **降低延迟**：6 个 NPC 的 LLM 调用可以并行发出，实际等待时间 ≈ 单次调用时间
- **利用 prompt cache**：如果所有 NPC 共享相同的静态 prompt 前缀，并行请求可以命中同一份缓存

### 2.3 串行结算的必要性

- 避免两个 NPC 同时"买走最后一份补给"
- 确保行动按照合理的优先级执行（如先到先得、或按行动速度排序）
- 所有状态变更通过单一路径，审计清晰

## 三、冲突解决策略

当多个 Agent 的行动相互矛盾时：

| 冲突类型 | 解决规则 | 示例 |
|---|---|---|
| 资源竞争 | 先提交者优先，后来者收到"资源不足"反馈 | 两人同时想买最后一件商品 |
| 空间冲突 | 均可进入，但触发遭遇事件 | 敌对 NPC 同时进入同一区域 |
| 社交冲突 | 双方都执行，结果叠加 | A 向 B 示好的同时 B 在疏远 A |
| 攻击冲突 | 启动战斗结算流程 | 两个 NPC 互相攻击 |

## 四、NPC 之间不直接通信

Claude Code 的子代理模式：子代理在隔离的 conversation scope 中运行 mini-loop，完成后返回**压缩结果**给父代理，而非共享完整 context。

**TinyMB 的对应设计**：

- NPC 之间**不直接共享 context**
- NPC 之间的"交互"通过世界状态间接实现：
  - NPC-A 在市集发表了演讲 → 事件记录写入世界状态
  - 下一步，NPC-B 的观察包中包含"你听说 NPC-A 在市集发表了支持商盟的演讲"
  - NPC-B 根据自己的性格和关系做出反应

这样做的好处：
- 每个 NPC 的 context 独立，不会因为某个 NPC 的长对话污染所有人的 token 预算
- 更符合"有限信息"的设计约束
- 可以自然地实现"信息不对称"——不同区域的 NPC 收到不同的事件摘要

## 五、共享前缀优化 Cache

Claude Code 的 coordinator 有一个精巧设计：所有 fork 出的子代理使用**共享 prompt 前缀**（如 `Fork started — processing in background`），提升 prompt-cache 前缀命中率。

**TinyMB 应用**：

```
所有 NPC 的 prompt 结构：

[共享静态前缀]              ← 所有 NPC 相同，cache 命中
  世界观 + 规则 + 行为框架
  当前世界公共状态（天数、繁荣度、物价）
[NPC 特有部分]              ← 每个 NPC 不同
  角色身份 + 性格
  个人状态 + 关系
  观察包
```

如果用的是支持 prompt caching 的 API（如 Claude API），6 个 NPC 的并行请求可以共享一份静态前缀的缓存，大幅降低成本。

## 六、Verification Agent 的游戏版应用

Claude Code 有独立的验证 agent，对实现进行对抗性审查。

**TinyMB 可以考虑一个"世界一致性检查 agent"**：

- 在每个结算周期后运行
- 检查世界状态是否自洽（如角色不能同时在两个区域）
- 检查经济数值是否在合理范围（防止通胀/崩溃）
- 检查 NPC 行为是否符合角色设定（如一个胆小的角色不应频繁主动攻击）

这不需要是一个 LLM agent，用规则引擎做基础检查即可。只在检测到异常时才调用 LLM 做深入分析。

[TinyMB 对接] 风险 R3（NPC 行为同质化）和 R4（经济崩溃/通胀）都可以通过这个机制早期发现。
