# 行动系统与工具治理

> 核心问题：从 Claude Code 14 步工具治理链精简出适合 TinyMB 的游戏行动管线。

---

## 一、Claude Code 的 14 步工具治理链

[源码锚点] 综合 `Tool.ts`（工具接口 + buildTool 工厂）、`tools.ts`（工具注册与预设）、`permissions.ts` 和各来源分析。

```
1.  解析 agent 输出 → 提取工具调用
2.  Schema 校验
3.  validateInput() → 输入级检查
4.  推测分类器（speculative classifier）→ 自动判断安全性
5.  PreToolUse hook → 可改写/拦截
6.  权限决策（allow / deny / ask user）
7.  输入修正（fix-up）
8.  tool.call() → 实际执行
9.  遥测记录
10. PostToolUse hook → 后处理/连锁触发
11. 结构化成功/失败结果返回
12. 结果追加到 messages[]
13. 判断是否继续循环
14. 上下文管理（压缩/折叠判断）
```

### 关键设计原则

- **Fail-closed 默认值**：`isConcurrencySafe` 和 `isReadOnly` 默认 false，未声明的工具按高风险处理
- **Edit 必须先 Read**：是工具级硬约束，不是 prompt 建议——违反会直接报错
- **每个工具有完整元数据**：短描述、长"how to use" prompt、schema、call 函数、UI 渲染 hook、permission hook、validation hook

## 二、TinyMB 精简版：5 步行动管线

TinyMB 不需要 14 步的复杂度，但核心治理逻辑可以压缩为 5 步：

```
┌──────────────────────────────────────────────────┐
│ Step 1: 解析 → Agent 输出结构化行动意图（JSON）     │
│         - 校验 JSON 格式是否合法                    │
│         - 校验是否符合行动 schema                   │
│         - 格式不合法 → 重试一次 → 仍失败 → 默认行为  │
├──────────────────────────────────────────────────┤
│ Step 2: 前置校验 → 规则引擎判断行动是否合法          │
│         - 角色在当前位置能执行此行动吗？             │
│         - 资源够吗？前置条件满足吗？                 │
│         - 时间步内还有行动机会吗？                   │
│         - 不合法 → 返回拒绝原因给 Agent             │
├──────────────────────────────────────────────────┤
│ Step 3: 请示判断（仅玩家 Agent）                    │
│         - 根据行动风险等级和自主等级设置             │
│         - 需要请示 → 暂停，等待玩家确认/否决/修改    │
│         - 不需要 → 继续                             │
├──────────────────────────────────────────────────┤
│ Step 4: 执行 → 修改世界状态                         │
│         - 扣除资源                                  │
│         - 更新角色位置/状态                          │
│         - 计算行动结果（含随机性）                   │
│         - 写入审计日志                               │
├──────────────────────────────────────────────────┤
│ Step 5: 后处理 → 连锁效果                           │
│         - 触发事件（如攻击 → 关系变化）              │
│         - 更新 NPC 对玩家的评价                      │
│         - 生成日记素材                               │
│         - 检查是否触发特殊事件/剧情                  │
└──────────────────────────────────────────────────┘
```

## 三、行动注册表设计

参考 Claude Code 的工具注册模式，每个行动类型应该有完整的元数据：

```json
{
  "action_id": "trade_buy",
  "display_name": "购买商品",
  "description_short": "在市集区购买指定商品",
  "description_long": "从市集区的商人处购买商品。需要角色在市集区，且持有足够金币。价格受物价指数影响。",
  "available_zones": ["market"],
  "schema": {
    "item": "string",
    "quantity": "integer",
    "target_merchant": "npc_id (optional)"
  },
  "preconditions": [
    "character.zone == 'market'",
    "character.money >= item.price * quantity"
  ],
  "risk_level": "low",
  "requires_consultation": false,
  "time_cost": 0,
  "effects": {
    "money": "-(item.price * quantity)",
    "inventory": "+item * quantity",
    "relationship_merchant": "+1"
  },
  "post_hooks": ["update_market_prices", "check_trade_achievement"]
}
```

## 四、从 Claude Code 学到的关键模式

### 4.1 PreAction Hook（对应 PreToolUse）

在行动执行前可以修改或拦截：

- **拦截**："你没有足够金币"→ 返回错误给 Agent
- **修改**："商品价格刚刚涨了"→ 调整实际费用
- **警告**："这会严重得罪守备军团"→ 追加信息给 Agent（如果自主等级允许继续则不阻止）

### 4.2 PostAction Hook（对应 PostToolUse）

在行动执行后触发连锁效果：

- 攻击行为 → 降低名誉（Honor）
- 帮助 NPC → 提升关系值
- 进入敌对区域 → 触发随机遭遇
- 完成关键任务 → 推动剧情

### 4.3 Bash Security 的启发

Claude Code 的 `bashSecurity.ts` 有 23 条安全检查，防止各种绕过攻击。游戏中"Agent 试图作弊"是类似问题：

- LLM 输出了不存在的行动类型 → schema 校验拒绝
- LLM 试图"声称"自己有某个道具 → 以 Runtime 状态为准，忽略 Agent 声称
- LLM 输出了超出行动范围的效果 → 只执行注册表中定义的 effects

### 4.4 Lazy Loading 工具清单

Claude Code 不是每次都把全部 40+ 工具描述塞给模型，而是按需注入（如 ToolSearchTool 做延迟加载）。

**TinyMB 应用**：NPC 在不同区域有不同的可用行动。不要每次都把全部行动清单塞进 prompt——只提供当前位置可执行的行动，减少 token 消耗和决策混乱。

## 五、行动风险分级

参考 Claude Code 的权限分级（read-only 工具无需权限，写操作需要权限，危险操作强制确认），TinyMB 的行动可以分为：

| 风险等级 | 定义 | 示例 | 请示策略 |
|---|---|---|---|
| 无风险 | 纯信息获取 | 查看区域信息、查看关系 | 永远自主 |
| 低风险 | 可逆的日常行为 | 移动、小额交易、普通对话 | 默认自主，可配置请示 |
| 中风险 | 有明显代价的行为 | 大额交易、招募随从、接受任务 | 默认请示 |
| 高风险 | 不可逆或影响重大 | 攻击行为、站队表态、资源全投 | 强制请示 |
| 极高风险 | 游戏关键转折点 | 背叛派系、挑战城主 | 强制请示 + 确认对话 |

[TinyMB 对接] 极简骑砍规则集 §2.1："默认自主 + 重要请示 + 安全回退"。此处给出的分级是该策略的具体化。
